## 1. `machinespirit.diagnose()` reports `ready: True` with no servers running

**FIXED 2026-07-30.** Resolution and its verification are at the end of this
section; the finding is kept in full because the reasoning is what stops it
being reintroduced.

**Confirmed by reproduction. Highest-value finding.**

Two independent flaws in the function whose entire documented purpose is
"Which part is missing, rather than that something is."

**a. The unpooled probe accepts any HTTP 200.** `available()`
(`core/machinespirit.py:146`) reads `/health`. llama.cpp does not
authenticate that route, so a bad key still returns 200 and any unrelated
server satisfies it.

**b. The pooled probe never touches the network.**
`diagnose()["pooled"]` (`core/machinespirit.py:339`) calls
`embedding_server.available()`, which is
`EMBED_ENABLED and os.path.isfile(EMBED_MODEL_PATH) and _url_is_loopback(...)`
— a configuration check. It is True whenever the model *file* exists.

Measured with **no llama-server running at all**:

```
embedding_server.available()       = True     <- becomes diagnose()["pooled"]
embedding_server._health_responds()= False
embedding_server.is_alive()        = False    <- the correct check, unused here
```

And with a throwaway server on 8084 answering `/health` with 200 and 401ing
everything else — the shape of the stale `sable-anchor-field-check` server
that cost an hour on 2026-07-29:

```
machinespirit.available()       = True
machinespirit.trajectory('hello') = None
diagnose() -> configured True, unpooled True, pooled True, ready True, reason None
```

`ready: True`, `reason: None`, and the caller gets `None`.

**Confirmed live in Super Dev Hazard**, against the real unpooled server on
8084 and the real anchor dictionary — not a stub. Baseline with both
embedders up, tracing "a chirping carbon monoxide alarm":

```
trajectory()     : 10 tokens
anchor_vectors() : 184 anchors
readout          : 'a fire alarm during an exam' 0.374 @8;
                   'the silence after a loud noise' 0.305 @3
```

The pooled server on 8082 was then killed, leaving 8084 up:

```
pooled 8082 is_alive()   = False      <- it is genuinely gone
pooled 8082 available()  = True       <- what diagnose() reads
diagnose() -> configured True, unpooled True, pooled True,
              tokens 10, ready True, reason None
anchor_vectors()         = None
readout                  = (empty)
```

This is worse than the stub case. The unpooled half still works, so
`diagnose(text=...)` reports `tokens: 10` — which reads as positive evidence
that the pipeline is healthy — alongside `ready: True` and `reason: None`,
while the trace produces nothing at all. The single honest signal,
`anchor_vectors()` returning `None`, is silent by design.

It lands exactly where `anchor_vectors():202` predicted in its own docstring:
"A trace that fails because the pooled embedder is absent looks identical to
one that fails because the unpooled one is." `diagnose()` was written to
resolve that ambiguity and does not.

The consequence is inverted messaging. The branch at `:364` that says *"the
ordinary embedding server is not [running]"* can only fire when the model
**file** is missing — a configuration problem. During a real pooled-server
outage `status["pooled"]` stays True, the branch is skipped, and `ready`
becomes True. The docstring warns that "reporting a pooled-server outage as
an unpooled one sends the operator to restart the wrong process"; the code
reports it as no problem at all.

**Fix**: `diagnose()` should call `embedding_server.is_alive()` for the
pooled half, and `available()` should verify an authenticated route and the
`--pooling none` identity, mirroring `embedding_server.is_alive():170`.
The pattern is already written, one module over.

Carried unfixed across two handoffs. Repro script preserved in the session
scratchpad as `repro_8084.py`.

### Resolution

Both halves now use the pattern the sibling modules already had.

- `available()` probes `/v1/models` **with the key** instead of `/health`,
  and requires the response to carry at least one model id. It does not
  claim to verify `--pooling none`; there is no route that reports pooling,
  and the docstring says so rather than implying a guarantee it cannot make.
- `diagnose()["pooled"]` reads `embedding_server.is_alive()`. It is still
  computed before the `configured()` early return, because `reconstruct`
  reads that field alone and needs it meaningful in ordinary mode.
- The reason text now separates a stopped process from an absent model, so
  the repair it names is the repair that is needed.

**Eight tests added**, in `DiagnoseTests` and a new `UnpooledProbeTests`.
Verified to fail against the unfixed source — reverting `machinespirit.py`
alone produces 5 failures, including `assertFalse(ms.available())` raising
`True is not false` for the health-only squatter.

The existing `test_pooled_down_is_reported_as_the_pooled_one`, whose
docstring called it "the regression this function exists for", was passing
because its helper stubbed `embedding_server.available()` — the
configuration check. It simulated a missing model file and called it an
outage, so the test carried the same conflation as the code. The helper now
stubs liveness and configuration separately.

Re-verified live, against the real servers rather than a stub:

| state | before | after |
| --- | --- | --- |
| both up | `ready True` | `ready True`, identical readout and scores |
| pooled 8082 killed | `pooled True, tokens 10, ready True, reason None` | `pooled False, ready False`, reason names a *stopped server rather than a missing file* |

Suite: no failures, 2 skips.

## 2. The regression suite starts a real llama-server and leaves it running

**Confirmed.** Chain:

`tests/test_regressions.py:3007` calls `assistant_main.main()` →
`main.py:3237` spawns `threading.Thread(target=_start_semantic_layer, daemon=True)`
→ `_start_semantic_layer` (`main.py:680`) → `embedding_server.start()`
(`main.py:693`) → a real `llama-server.exe`.

Verified by killing every llama-server, running the suite, and finding a new
process created 09:43:20 — mid-run — still alive after the runner exited 0.
`run_regressions.py` does nothing after the tests; the process is a leak.

The same thread also reaches `semantic_index.start_worker()`,
`history_recall.refresh()` and `knowledge_library.request_embedding()`
against real state.

This is the family the previous session documented: a test touching a live
subsystem. That test is otherwise careful — it patches `start_server`,
`_prepare_voice_for_startup`, `memory_worker`, and `_record_session_rhythm`,
with a comment explaining that the last one would otherwise file the suite's
duration as one of the operator's sessions. The background thread was missed.

Consequences: the suite is not hermetic, a server accumulates on each run,
and successive runs take a different branch (`is_alive()` True) than the
first — so the suite is order-dependent on its own history.

**Fix**: patch the thread spawn, or `_start_semantic_layer`, in that test.

## 3. The edit-guard deny lists fail open on rename

**Latent, security-relevant, not currently triggered.**

`DENIED_FILES` (13), `MAINTENANCE_DENIED_FILES` (13) and
`AUTONOMOUS_ALLOWED_FILES` (5) in `editing/edit_guard.py` name files by path.
**All 31 exist today. No test asserts that they do.**

`resolve():322` denies by exact name match; `list_editable_files():353`
includes any file `resolve()` does not refuse. So renaming a protected file
silently removes its protection and widens the editable surface — the deny
list fails **open**.

The files behind those entries are `core/persona.py`, `core/dev_auth.py`,
`core/agent_interface.py`, `main.py`, `commands/command_handlers.py` and
similar. The module's own comment says a constraint the constrained thing can
edit is decoration; a rename makes it decoration silently.

`list_autonomous_files():363` intersects the allowlist with the editable set,
so the unattended path fails closed. Only the human-confirm and maintenance
surfaces are exposed.

**Fix**: the test the last session wrote for `INCLUDE_FILES` —
`test_every_whitelisted_file_actually_exists` — applied to these four lists.

## 5. Line endings — the foot-gun's root cause, measured

`core.autocrlf=false` and **no `.gitattributes`**, so whatever is written is
committed.

- **15 files are CRLF**, including `ui/ui.py`, `commands/command_handlers.py`,
  `core/tutorial.py`, `core/dev_auth.py`, `editing/super_dev_engine.py`.
- **3 files carry a UTF-8 BOM**: `tools/machinesoul.py`,
  `tests/test_machinesoul.py`, `tests/test_machinespirit.py`.
- **3 files are committed with mixed endings inside one file** —
  `editing/approval_manager.py` (`i/mixed`), `editing/change_planner.py`,
  `project/project_analyzer.py`.

Mixed endings within a single tracked file are the fingerprint of exactly the
scripted-rewrite accident the handoff records. A `.gitattributes` pinning
`*.py text eol=lf` would end the whole class.
